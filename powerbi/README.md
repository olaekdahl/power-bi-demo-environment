# PL-300 Demo Power BI Solutions

Two Power BI Projects (`.pbip`), both generated by
[`../scripts/generate-pbip.py`](../scripts/generate-pbip.py) — **edit the generator,
not these files**, then regenerate.

| Solution | Data | Opens with | Use it for |
|---|---|---|---|
| `PL300-Demos.pbip` | Inline M `#table` literals | No prompts at all | Handing out. DAX filter context, R, Python and a static spatial page. |
| `PL300-Spatial-SQL.pbip` | Live `Sql.Database` → `PL300Demo` | A credential prompt, and only on the VM | Showing that the spatial results really come from SQL Server. |

```bash
# The inline-literal solution (needs the CSV export first)
./scripts/export-spatial-csv.sh
python scripts/generate-pbip.py --out powerbi --sql-dir .spatial-export

# The live-SQL solution (reads the views directly, so no export)
python scripts/generate-pbip.py --solution spatial-sql --out powerbi

python scripts/validate-pbip.py powerbi          # checks against Microsoft's schemas
```

Regenerating either one is idempotent, produces byte-identical output, and leaves
the other solution — and this README — untouched. The generator deletes only the
paths the chosen solution owns; a blanket clean once ate this file.

# 1. `PL300-Demos.pbip` — inline literals

Six pages over a five-table model. Every table is an inline `#table` literal, so
the file opens with no data source and no credential setup, which is what makes it
safe to hand to a class and possible to validate automatically.

| # | Page | Status |
|---|---|---|
| 1 | Overview | **Renders.** Cards, category table, revenue by month. |
| 2 | Python visual | Needs a one-time paste — see below. |
| 3 | R visual (ggplot2) | Needs a one-time paste. |
| 4 | R forecast (ARIMA) | Needs a one-time paste. |
| 5 | SQL spatial (geography) | **Renders.** Azure Maps, lat/long scatter, WKT table. |
| 6 | CALCULATE (filter context) | Two tables, two cards, the formulas on canvas. Not yet screenshot-verified. |

Verified figures on page 1: total **$6,637,230.83** across **35,623 units**, which
reconciles exactly with `Regional_Sales_Report.pdf` in the demo data set.

| Table | Rows | Source |
|---|---|---|
| `CategorySales` | 4 | Contoso CSV, aggregated |
| `MonthlyRevenue` | 12 | Contoso CSV, aggregated |
| `CategoryMonthlySales` | 48 | Contoso CSV, aggregated |
| `StoreGeography` | 8 | **SQL** `dbo.vw_StoreLocations` + `dbo.vw_StoreCatchment` |
| `CustomerGeography` | 480 | **SQL** `dbo.vw_CustomerLocations` |

The two spatial tables are the real output of the SQL Server `geography` views,
materialised by `export-spatial-csv.sh`. That export is what makes this
reproducible: a rebuilt environment regenerates the same solution instead of
depending on CSVs somebody produced by hand.

`MonthName` carries `sortByColumn: MonthNumber`, without which a text month sorts
alphabetically and the axis reads April, August, December…

## Making the R and Python visuals render

The script bodies are in the report *and* as standalone files in
[`scripts/`](scripts/). Power BI does not load an externally-authored script body
while the report is in PBIR-Legacy form (see below), so do this once per visual:

1. Select the visual. The script editor opens at the bottom.
2. Open the matching file, copy all of it, and paste over the editor's contents
   (`Ctrl+A`, `Ctrl+V`).
3. Click the ▷ run button in the script editor header.

| Page | File |
|---|---|
| 2. Python visual | `scripts/python-category-revenue.py` |
| 3. R visual | `scripts/r-ggplot-category.R` |
| 4. R forecast | `scripts/r-forecast-arima.R` |

Expected results, confirmed on this VM: the Python and ggplot2 visuals draw four
horizontal bars with Camping highest at ≈$3.30M; the forecast visual titles itself
**ARIMA(2,0,0)** and projects 678,184 / 679,910 / 632,080 for the next three months.

The first time you open the report Power BI asks to **Enable script visuals** —
accept it. Pressing Escape *cancels* that prompt, which leaves every script visual
blank with no error message anywhere.

## Page 6 — CALCULATE and filter context

Five measures on `CategoryMonthlySales`, and nothing else. One table was chosen on
purpose: it already carries both dimensions the lesson needs (`Category` and
`MonthName`) plus the amount, so filter context can be changed and re-changed with
no relationship anywhere in the picture. Relationships and filter propagation are a
separate lesson, and teaching both at once is what makes CALCULATE feel like magic.

The left table has `Category` on rows, and every figure below is exact:

| Category | Sales | Sales Camping | Sales Camping Kept | Sales All Categories | Category Share % |
|---|---|---|---|---|---|
| Apparel | $1,580,293 | $3,302,900 | *(blank)* | $6,637,231 | 23.8% |
| Camping | $3,302,900 | $3,302,900 | $3,302,900 | $6,637,231 | 49.8% |
| Cooking | $533,589 | $3,302,900 | *(blank)* | $6,637,231 | 8.0% |
| Hiking | $1,220,450 | $3,302,900 | *(blank)* | $6,637,231 | 18.4% |
| **Total** | **$6,637,231** | **$3,302,900** | **$3,302,900** | **$6,637,231** | **100.0%** |

Three constant columns beside one that varies is the whole lesson, and the columns
to put side by side are **Sales Camping** and **Sales Camping Kept**. Same filter,
one wrapped in `KEEPFILTERS`: the first *replaces* the row's own Category filter, so
all four rows read Camping's number; the second *intersects* with it, so three rows
go blank. "CALCULATE overrides the filter context" is the half-truth this corrects.

The right-hand table projects the **same** `[Sales Camping]` measure with `MonthName`
on rows — where there is no Category filter to replace, so it simply applies:

| Month | Sales | Sales Camping |
|---|---|---|
| January | $316,904 | $149,950 |
| February | $323,268 | $168,202 |
| … | | |
| December | $613,311 | $313,079 |
| **Total** | **$6,637,231** | **$3,302,900** |

Four more variants — a comparison filter, two ANDed filter arguments, table-wide
`REMOVEFILTERS`, and `ALLSELECTED` — are in
[`scripts/calculate-filter-context.dax`](scripts/calculate-filter-context.dax), each
with its expected answer in a comment. They are deliberately *not* in the model:
adding one with **Modeling → New measure** and watching the number match the comment
is the exercise. The five shipped measures in that file are emitted from the same
list that writes them into `model.bim`, so it cannot claim a formula the page does
not render.

Visual titles do not survive PBIR-Legacy, so every label the lesson depends on is a
textbox, and the table columns are left showing raw measure names. That is the right
outcome here — `Sales Camping Kept` as a column header is exactly what you want the
class reading while you talk through the formula.

# 2. `PL300-Spatial-SQL.pbip` — live from SQL Server

Seven tables, all bound to views in `PL300Demo` on the demo VM. Nothing is
materialised: every number on screen was computed by SQL Server's spatial types
when the visual asked for it.

Storage mode reads **Mixed** in the status bar — six DirectQuery tables plus one
Import table, which is a composite model.

## Why DirectQuery

Measured on the VM, not assumed. Every view answers in well under 50 ms:

| View | Rows | Elapsed |
|---|---|---|
| `vw_RegionBoundaries` | 4 | 1 ms |
| `vw_CustomerLocations` | 480 | 2 ms |
| `vw_StoreCatchment` | 8 | 9–10 ms |
| `vw_CustomerNearestStore` | 480 | 21–23 ms |
| `vw_AdventureWorksAddresses` | 19,614 | 46 ms |

The two that *sound* expensive are the two that were timed most carefully.
`vw_StoreCatchment` cross-joins 8 stores against 480 customers and evaluates
`STDistance` for all 3,840 pairs — and collapses to 8 rows in about 10 ms.
`vw_CustomerNearestStore` does `CROSS APPLY (SELECT TOP 1 … ORDER BY STDistance)`
per customer in about 22 ms. Nothing here is near DirectQuery's 1,000,000-row
intermediate limit.

`AdventureWorksAddresses` is Import, and deliberately the only one. It makes the
status bar read Mixed, it shows 19,614 rows in Data view beside six tables that say
*"DirectQuery tables can't be shown"*, and stopping the SQL Server service breaks
pages 1–4 while page 5 keeps rendering. It is also a relationship island, so the
model contains no Import-to-DirectQuery relationship and therefore no limited
relationships.

## The M is navigation, not a native query

```m
let
    Source = Sql.Database("localhost", "PL300Demo"),
    dbo_vw_StoreLocations = Source{[Schema="dbo",Item="vw_StoreLocations"]}[Data]
in
    dbo_vw_StoreLocations
```

Not `Sql.Database(server, db, [Query = "SELECT …"])`. A native query raises the
**native database query** approval dialog for every distinct query text — a
guaranteed stall in front of a class — and stops the mashup engine folding, which
greys out **View Native Query**. All the SELECT logic already lives in the views,
so a native query would buy nothing.

All five verified by screenshot against the database.

### Say the expected answer out loud before you click

Pages 3 and 4 are validation checks that currently **pass**, so both headline cards
read **0**. That is correct, not broken — but an instructor who walks up cold and
sees a zero will assume the demo is dead. The data makes disagreement impossible:
`create-spatial-demo.sql` scatters each customer within roughly ±0.45° latitude of
its *own* store (max observed 65.44 km) while the eight stores sit in eight
far-apart cities, so no customer is within 100 km of any store but its own. That is
also why the 100 km bar on page 2 is flat at 60 — exactly 480/8.

To make it non-zero live, one statement, and because the tables are DirectQuery the
cards move on the next click with **no refresh**:

```sql
-- three Austin customers physically relocated to Bellevue
UPDATE dbo.CustomerLocation
SET GeoPoint = geography::Point(47.6104, -122.2007, 4326)
WHERE CustomerID IN ('C1301','C1302','C1303');
```

`Reassignment Candidates` then reads 3 and the match rate 99.4%. For page 4, move a
store instead — `UPDATE dbo.StoreLocation SET RegionID = 2, RegionName = N'North'
WHERE StoreID = 1;` makes Bellevue report Assigned North / Contains West / MISMATCH.
Undo before re-running `create-spatial-demo.sql`, which `RAISERROR`s on any
mismatch. The script is deterministic — the offsets are a function of row number,
not `RAND()` — so re-running it restores the original data exactly.

## First-run checklist on the presenting machine

1. **Credentials.** Expect a SQL Server authentication prompt on first open. They
   live in the per-user store, never in the `.pbip`, so every machine prompts fresh.
2. **Encryption warning** for the unencrypted localhost connection, and possibly
   *"The certificate chain was issued by an authority that is not trusted"* —
   `PBI_SQL_TRUSTED_SERVERS` fixes that one.
3. **Composite model warning.** Power BI shows one the first time. Both sources here
   are the same SQL Server instance, so the exposure it warns about is nil.
4. **Refresh once** to populate the Import table. DirectQuery pages need no refresh.
5. **Azure Maps** needs the tenant switch in Admin Portal → Integration, and reaches
   Azure for tiles. Pages 3 and 4 use scatter charts instead, so a locked-down room
   degrades the demo rather than killing it.
6. **Restart Desktop after hand-editing `model.bim`.** Desktop is not aware of
   external file changes and can resurrect old metadata from `.pbi/cache.abf`.

# What the legacy report format really drops

Both solutions emit the report twice:

- **`<name>.Report/report.json`** — PBIR-Legacy. What Power BI Desktop actually
  reads on a stock install, so it is what makes these work today.
- **`<name>.Report/definition/`** — PBIR. The documented, per-file, schema-validated
  format, ready for when you enable the preview feature.

Microsoft is blunt about the first: *report.json "contains the report definition in
the Power BI Report Legacy format (PBIR-Legacy) and **doesn't support external
editing**"*. Concretely, and all confirmed by screenshotting these solutions:

| Authored | Survives? |
|---|---|
| Visual type, position, field bindings | Yes |
| `textbox` content (`objects.general.paragraphs`) | Yes — which is why all narration is in text boxes |
| Visual titles (`visualContainerObjects.title`) | **No.** Titles come out auto-generated: "CustomersWithin50km by City" |
| R/Python script bodies (`objects.script`) | **No.** The editor opens empty, with no error |
| Column captions (`nativeQueryRef` → `NativeReferenceName`) | **No.** Headers read "StoreName", "Average of Latitude" |

The last one has a practical consequence: model column names *are* the captions, so
keep them presentable and leave table visuals wide enough for the unaliased header.

PBIR fixes the first two, because `visual.json` separates the concerns —
`visual.visualContainerObjects.title` for chrome, `visual.objects.script` for the
data view.

## Switching to PBIR

1. In Power BI Desktop: **File → Options and settings → Options → Preview features**
   → tick **Store reports using enhanced metadata format (PBIR)**. Restart Desktop.
2. Regenerate with `--pbir`, which sets `definition.pbir` to version `4.0`.

Do these in that order. A `version: 4.0` project on a Desktop *without* the preview
feature does not open at all — Power BI starts a blank "Untitled" report and says
nothing. That asymmetry is why `1.0` is the default.

The `definition/` folder is emitted and schema-validated either way, so
`validate-pbip.py` catches shape errors in about a second rather than one
five-minute render at a time.

# Two visual traps worth knowing

**`columnChart` is the *stacked* column chart.** The catchment page plots three
cumulative buffers (25/50/100 km), and stacked they added a number to itself:
Bellevue rendered as 15+52+60 = 127, a total that means nothing and that nobody
questions from the back of a room. Use `clusteredColumnChart`.

**Azure Maps geocodes its Location field, and that beats latitude/longitude.** With
`RegionName` in Location, Power BI geocoded the words "East", "North", "South",
"West" and put the South bubble in the middle of the Atlantic — silently — while
the four real `EnvelopeCenter` coordinates sat unused in the model. Removing
Location entirely renders *zero* marks, so there is no coordinates-only mode to fall
back to. Page 1 keeps a real map because its Location field is `City`, which
geocodes correctly; page 4 uses a scatter, where longitude and latitude are just
numbers and nothing gets looked up.

Related: don't bind Size to a narrow range. `CustomersWithin50km` spans 44–52, and
Azure Maps stretched that 15% spread across the full bubble scale — Austin came out
at a tenth of Bellevue's diameter. Magnitudes belong on a chart with an axis.
